# Open-Weight Small/Medium LLM Landscape (1B-14B) for a Rust Trading-Platform AI Agent, Late 2026

Scope note: this covers two use cases — (A) constrained/closed-schema structured output & classification (decision enum, `deny_unknown_fields`), and (B) tool-calling + general chat against a typed read-only tool registry. Research was done via web search in Nov 2026; several facts rest on secondary/aggregator sources because official model cards and license files were not always directly retrievable. Those gaps are flagged explicitly below — verify primary sources (Hugging Face model card "Files" tab LICENSE, ai.meta.com/llama, ai.google.dev/gemma/terms) before committing to a choice.

## 1-4B range: structured-output reliability & fine-tunability (candidates: Qwen3, Llama 3.2, Phi-4-mini, Gemma 3, SmolLM3)

### Takeaway
For the 1-4B tier, **Qwen3 (0.6B/1.7B/4B, Apache 2.0)** and **SmolLM3-3B (Apache 2.0)** are the strongest fits for a closed-schema/classification task: both are natively agent/tool-call-oriented, fully permissive-licensed, and have published BFCL tool-calling scores. **Phi-4-mini (3.8B, MIT)** is a credible permissive alternative with a documented (if imperfect) function-calling format. **Gemma 3** small variants (1B/4B) are permissively-licensed-with-conditions (Gemma Terms of Use, not Apache/MIT) and rely entirely on prompt-engineering for structured output — Google's own docs confirm Gemma 3 has no built-in grammar/schema enforcement, so reliable closed-schema output requires an external constrained-decoding layer (e.g., llama.cpp GBNF/JSON-schema grammars) regardless of model choice. **Llama 3.2 1B/3B** is usable but is the most license-encumbered of the group (naming/attribution/notice obligations, "Built with Llama" branding requirement, and a monthly-active-user threshold that triggers a separate Meta license).

### Cited Findings
- Qwen3 dense models 0.6B-14B (plus 30B-A3B/235B-A22B MoE) are released under Apache 2.0 with no "acceptable use" clause and no research-only restriction, per multiple secondary comparison sources — [Claude Market Blog](https://claudemarket.ai/blog/best-qwen-models-2026); confirmed directly on the official Qwen3-4B Hugging Face model card metadata, which lists `License: apache-2.0` — [Qwen/Qwen3-4B on Hugging Face](https://huggingface.co/Qwen/Qwen3-4B).
- Qwen3-4B natively supports 32,768 tokens, validated to 131,072 tokens via YaRN rope scaling; the card states "Qwen3 excels in tool calling capabilities" and recommends the Qwen-Agent framework for agentic use, with agent capabilities in both "thinking" and "non-thinking" modes — [Qwen/Qwen3-4B on Hugging Face](https://huggingface.co/Qwen/Qwen3-4B).
- SmolLM3-3B is Apache 2.0 for both base and instruct checkpoints, released July 2025, with full training-data/config transparency published by Hugging Face — [European Open Source AI Index](https://osai-index.eu/model/smollm), [SmolLM3-3B model card](https://huggingface.co/HuggingFaceTB/SmolLM3-3B).
- SmolLM3-3B's native context is 64K tokens (config default), extendable to 128K via YaRN/rope_scaling change; tool calls can be emitted as JSON blobs inside XML tags or as Python-style calls; recommended serving via `vllm serve HuggingFaceTB/SmolLM3-3B --enable-auto-tool-choice --tool-call-parser=hermes` — [SmolLM3-3B model card](https://huggingface.co/HuggingFaceTB/SmolLM3-3B).
- On BFCL (Berkeley Function-Calling Leaderboard), SmolLM3-3B scores 92.3 in non-reasoning mode and 88.8 in extended-thinking mode, versus 95.0 for Qwen3-4B on the same comparison — [KDnuggets: 5 Small Language Models for Agentic Tool Calling](https://www.kdnuggets.com/5-small-language-models-for-agentic-tool-calling).
- Phi-4-mini-instruct is licensed MIT, is 3.8B parameters (listed as "4B" on the HF page), supports 128K context, and has a documented "Tool-enabled function-calling format" section in its model card using `<|tool|>...<|/tool|>` wrapper tokens in the system prompt; the card itself notes the model "sometimes hallucinated function names or URLs in function-calling scenarios" — [microsoft/Phi-4-mini-instruct on Hugging Face](https://huggingface.co/microsoft/Phi-4-mini-instruct).
- The Phi-4-mini model card does not describe JSON-schema-constrained decoding or a structured-output guarantee — tool specs are passed as JSON text in the prompt, which is an input format, not an output guarantee — [microsoft/Phi-4-mini-instruct on Hugging Face](https://huggingface.co/microsoft/Phi-4-mini-instruct).
- Gemma 3 function calling is prompt-driven only: Google's own docs describe a system prompt listing functions, with the model told to reply in a specified JSON-like format; "the Gemma model does not emit tool-specific tokens; the framework must detect tool calls by checking whether the output matches the prompted format" — [Gemma function calling docs (ai.google.dev)](https://ai.google.dev/gemma/docs/capabilities/function-calling?hl=ja).
- A Hacker News discussion including Gemma team commentary states the model does not enforce grammar on its own ("nor does any raw model"); reliable schema-constrained output requires an external grammar/constrained-decoding layer such as llama.cpp's GBNF/JSON-grammar support or framework-level structured-output features (e.g., in Ollama) — [HN thread on Gemma function calling](https://hn.matthewblode.com/item/43451406).
- A specialized variant, **FunctionGemma**, built on Gemma 3 270M, is trained specifically for function calling with dedicated control tokens that base Gemma 3 lacks — [FunctionGemma formatting docs](https://ai.google.dev/gemma/docs/functiongemma/formatting-and-best-practices?authuser=5).
- Llama 3.2 1B/3B: license text (mirrored from Meta's Llama 3.2 Community License on Hugging Face) grants a non-exclusive, worldwide, non-transferable, royalty-free license covering use/reproduction/distribution/modification, with commercial use not excluded in the excerpt — [meta-llama/Llama-3.2-1B-Instruct LICENSE on Hugging Face](https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct/blob/main/LICENSE.txt).
- Llama 3.2 redistribution requires including a copy of the license agreement, displaying "Built with Llama" prominently on any related website/UI/documentation, and retaining the Llama attribution notice in a "Notice" file; fine-tuned/derivative models that are distributed must include "Llama" in the model name — [Llama 3.2 Community License mirror](https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct/blob/main/LICENSE.txt).
- Llama 3.2's license imposes a monthly-active-users threshold: entities above a set MAU count on the release date must request a separate license directly from Meta, granted at Meta's discretion; the Acceptable Use Policy is incorporated by reference — [Llama 3.2 Community License mirror](https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct/blob/main/LICENSE.txt).
- IBM released **Granite 4.0 Nano** — four instruct models plus base counterparts spanning 350M-1.5B parameters, aimed at edge/browser use, released October 2025 — all under Apache 2.0 — [Pulse.bot coverage of Granite 4.0 Nano](https://www.pulse.bot/ai/news/ibms-open-source-granite-40-nano-ai-models-are-small-enough-to-run-locally-directly-in-your-browser-da21fc62-e5d0-4beb-bfdb-d5186a61c0c2/). This is a newer (2025/2026-adjacent) small-model entrant worth a look for the 1-4B tier, though no tool-calling/BFCL data for it was found in this research pass.
- No evidence was found of a Llama 4 "small" (1B/3B-class) dense model; Llama 4 (Scout, etc.) is described as MoE and not positioned as a small on-device replacement for Llama 3.2 — [SourceForge SLM comparison, Aug 2026](https://sourceforge.net/software/small-language-models/integrates-with-code-llama/); one low-confidence source speculates about future "Llama 5" mobile-tier agentic models, explicitly unconfirmed.

### Inferences
- For use case A (closed-schema decision classification against a Rust enum with `deny_unknown_fields`), model choice matters less than the decoding layer: Qwen3-4B/SmolLM3-3B have native agentic/tool-call training that should make them follow format instructions more reliably out-of-the-box, but for a truly closed, fixed schema, pairing any of these small models with grammar-constrained decoding (llama.cpp GBNF generated from the JSON schema, or vLLM/outlines-style structured generation) is the safer architecture than relying on prompt-only compliance — this is consistent with the Gemma team's own admission that no raw model enforces grammar unaided.
- Apache 2.0 (Qwen3, SmolLM3, Granite Nano) and MIT (Phi-4-mini) are the cleanest licenses for a codebase with an AGPL-3.0 component elsewhere in the stack: both are permissive, have no copyleft/share-alike clause, and do not require source disclosure of the combined system, so there should be no license interaction with the AGPL-3.0 component for these weights (see Section 3 for the fuller discussion and its caveats).
- Gemma 3 and Llama 3.2, while nominally permissive-for-commercial-use, carry contractual redistribution conditions (notice files, branding like "Built with Llama"/"Built with Gemma", naming mandates for fine-tunes, use-restriction flow-down) that are legally distinct from open-source copyleft but still create compliance overhead not present with Qwen3/SmolLM3/Phi-4-mini/Granite — worth avoiding if minimizing legal surface area is a priority.

### Gaps
- No primary Microsoft source for Phi-4-mini's exact license was directly fetched in the first pass (secondary sources conflicted); this was resolved via a direct model-card fetch confirming MIT, but Microsoft's standalone license page was not independently cross-checked.
- No BFCL or equivalent tool-calling/structured-output benchmark score was found for Granite 4.0 Nano or for Gemma 3's small (1B/4B) variants specifically — only qualitative description of Gemma's prompt-only mechanism.
- No data found on fine-tunability specifics (e.g., LoRA/QLoRA community tooling maturity, PEFT adapter ecosystem size) per model — this would need a dedicated follow-up search of Hugging Face PEFT/LoRA adapter counts per base model.

## 7-14B range: tool-calling reliability & general chat quality (candidates: Qwen3 7B/14B, Llama 3.1/3.3 8B, Mistral 7B/Nemo, Phi-4 14B, Gemma 3 9B/12B, Hermes fine-tunes)

### Takeaway
**Qwen3-8B/14B (Apache 2.0)** is the best-documented native tool-caller in this range, with Qwen's own tooling (Qwen-Agent) and broad community vLLM/Ollama support. **Mistral Nemo 12B and Mistral Small 3 24B (both Apache 2.0)** are strong, fully-permissive general-chat/tool-use options — Mistral switched Small's license from its restrictive Research License to Apache 2.0 specifically to enable commercial deployment. **Hermes 4** (Nous Research) fine-tunes layered on Llama 3.1 70B/405B explicitly target function-calling + JSON-schema adherence and are well-regarded for this, but inherit the Llama Community License's redistribution conditions; a community-reported Hermes-4-14B variant built on Qwen3-14B would inherit Apache 2.0 instead, but that specific license claim is unconfirmed against an official card. **Gemma 3 9B/12B** remains prompt-only for tool calling (same caveat as the small variants) under the Gemma Terms of Use.

### Cited Findings
- Qwen3-8B and Qwen3-14B both support 128K context (extended via YaRN from a 32K native window), are Apache 2.0, and share the same "excels in tool calling capabilities" framing and Qwen-Agent recommendation as the 4B model — [Qwen/Qwen3-4B model card](https://huggingface.co/Qwen/Qwen3-4B) (describing the shared family docs) and secondary comparison sources — [digitalapplied.com Qwen models guide](https://www.digitalapplied.com/blog/qwen-models-complete-guide).
- Community reports on serving Qwen3 tool-calling: users running Qwen3-4B on vLLM used the `hermes` tool-call parser with `--enable-auto-tool-choice` successfully; separately, at least one user reported Qwen3's "native" (non-Hermes-format) tool-call mode failing on vLLM with empty arguments, while the default/Hermes-parser mode worked — i.e., native tool-call format support is serving-stack-dependent and the Hermes-style parser path is the more battle-tested route — [Reddit r/OpenWebUI via mirror](https://redlib.hbubli.cc/r/OpenWebUI/comments/1kv0oty/qwen34b_serve_with_vllm_native_tool_call_issue), community discussion aggregation — [haimaker.ai Qwen3-coder-hermes post](https://haimaker.ai/blog/qwen3-coder-hermes/).
- Mistral Nemo (12B, released July 2024) is Apache 2.0 with a 131,072-token context window — [OpenRouter Mistral Nemo listing](https://openrouter.ai/mistralai/mistral-nemo:free).
- Mistral Small 3 (24B, released January 2025) was released under Apache 2.0; Mistral explicitly changed policy here — previous Mistral Small releases used the Mistral Research License, which "prohibited commercial deployments unless you negotiate a commercial license with them" — [Simon Willison on Mistral Small 3](https://simonwillison.net/2025/jan/30/mistral-small-3/), [the-decoder.com coverage](https://the-decoder.com/new-mistral-small-3-does-more-with-less-under-apache-license/). No 2026 source was found indicating either Mistral license has since changed.
- Hermes 4 70B (Nous Research) is built on Llama-3.1-70B, is a "hybrid reasoning model... with toggleable deep thinking mode," and explicitly supports "JSON schema adherence, function calling, and reduced refusal rates"; the 405B variant built on Meta-Llama-3.1-405B is likewise emphasized for "function calling, structured JSON outputs, and multi-turn reasoning" — [oflight.co.jp Nous Hermes 4.3 guide](https://www.oflight.co.jp/en/columns/nous-hermes-4-3-function-calling-agent-guide-2026).
- Hermes licensing varies by base model: Hermes 3 (Llama-3-based) follows the Meta Llama License; Hermes 4.3 (built on ByteDance's Seed 36B) follows the ByteDance Seed License instead — these are different licenses for different Hermes generations/bases, not one uniform Hermes license — [fast.io Hermes LLM explainer](https://www.fast.io/resources/hermes-llm/), [oflight.co.jp guide](https://www.oflight.co.jp/en/columns/nous-hermes-4-3-function-calling-agent-guide-2026).
- A third-party aggregator lists "Hermes-4-14B" as fine-tuned from Qwen3-14B under Apache 2.0 — this is an unconfirmed secondary-source claim (not independently verified against an official Hugging Face card in this research pass) — [dev.co Hermes-4-14B listing](https://dev.co/ai/llms/hermes-4-14b).
- One commentary piece (secondary/blog-level) asserts the Llama 3 Community License "forbids training competing foundation models," which it frames as a complication for redistributing Llama-derived fine-tunes like Hermes commercially — flagged as unverified against Meta's primary license text — [fast.io Hermes LLM explainer](https://www.fast.io/resources/hermes-llm/).
- Gemma 3's function-calling mechanism (prompt-only, no dedicated tool tokens, no built-in grammar enforcement) applies across the family including the 9B/12B sizes; Google's own docs recommend the 27B variant for best tool-use performance and the 12B as a speed/quality balance point — [Gemma function calling docs](https://ai.google.dev/gemma/docs/capabilities/function-calling?hl=ja).
- NVIDIA released **Nemotron 3 Nano** as the smallest tier of a new Nemotron 3 family (with larger Nemotron 3 Super/Ultra tiers following in 2026); a prior generation, **Nemotron Nano 9B v2**, shipped with a "toggle on/off reasoning" feature — [VentureBeat on Nemotron Nano 9B v2](https://venturebeat.com/ai/nvidia-releases-a-new-small-open-model-nemotron-nano-9b-v2-with-toggle-on-off-reasoning), [Deccan Chronicle on Nemotron 3 family](https://www.deccanchronicle.com/technology/nvidia-unveils-new-open-source-ai-models-amid-boom-in-chinese-offerings-1924212). One secondary source lists Nemotron 3 Nano/Super alongside Qwen3-235B as having "solid tool calling" but gives no BFCL scores to substantiate this.
- No reliable, dated BFCL v4 open-weight leaderboard table could be retrieved directly (the live leaderboard page's rows were not present in the fetched content); BFCL v4 ("holistic agentic evaluation") was last updated 2026-04-12 per the page's own metadata, evaluation package `bfcl-eval==2025.12.17` — [Gorilla/BFCL leaderboard page](https://gorilla.cs.berkeley.edu/leaderboard.html). A single low-confidence secondary source (presenc.ai, not independently verified) claims top closed models score ~88-92% on some 2026 BFCL variant with leading open-weight models "within 5-10 points," and separately names xLAM, Watt-Tool, NexusRaven, and Hermes-Pro as open-weight tool-use-specialized models — treat this as an unverified lead, not a confirmed ranking.

### Inferences
- Among fully-permissive (Apache 2.0/MIT), well-documented-for-tool-calling options in the 7-14B range, Qwen3-8B/14B and Mistral Nemo 12B / Mistral Small 3 24B are the safest defaults for use case B, since they combine native tool-calling design with licenses that impose no redistribution/branding/notice obligations beyond standard Apache 2.0/MIT attribution.
- The Hermes family is attractive specifically because of its focused function-calling/JSON-schema fine-tuning, but the license inherited depends entirely on which base checkpoint is used (Llama-based Hermes carries Llama Community License obligations; a Qwen3-based Hermes variant, if the unverified claim holds, would carry Apache 2.0 instead) — this needs to be pinned down to a specific Hugging Face repo and its LICENSE file before adoption, not assumed from the family name.
- Given that Qwen3's "native" tool-call format shows at least one reported failure mode under vLLM while the Hermes-style parser path works reliably, the practical recommendation for a Rust-based serving stack is to standardize on the Hermes/ReAct-style tool-call parsing convention (widely supported across vLLM, Ollama, and llama.cpp tooling) rather than any single model's "native" format, regardless of which 7-14B model is ultimately chosen.

### Gaps
- No authoritative, current (2026) BFCL v4 leaderboard table with open-weight model scores was retrieved — the live page's table did not come through in the fetch, and no reliable aggregator replicated it with verifiable sourcing. This is the single biggest unresolved gap for quantitatively ranking tool-calling reliability across the 7-14B candidates; a direct re-fetch of gorilla.cs.berkeley.edu/leaderboard.html targeting the table markup, or of its underlying results JSON/GitHub repo, would be the next step.
- Phi-4 (full 14B, distinct from Phi-4-mini) was not directly researched in this pass — only Phi-4-mini (3.8B) was covered. Its license and tool-calling documentation should be checked separately (Microsoft has historically used MIT for the Phi-4 family, consistent with Phi-4-mini, but this was not independently confirmed for the 14B variant here).
- Llama 3.1/3.3 8B specifics (exact tool-calling format, BFCL score) were not directly researched in this pass beyond the general Llama Community License terms established for Llama 3.2; the license terms should be very similar (same Meta license family) but the exact text version (3.1 vs. 3.2 vs. 3.3 community license) should be verified per-model since Meta has issued separate license documents per release.

## Licensing deep-dive: commercial use, fine-tune redistribution, and AGPL-3.0 interaction

### Takeaway
Apache 2.0 (Qwen3, SmolLM3, Mistral Nemo/Small 3, IBM Granite Nano) and MIT (Phi-4-mini) are standard OSI-approved permissive licenses that unambiguously allow commercial use and redistribution of fine-tuned weights, carry no copyleft/share-alike obligation, and have no legal mechanism that would propagate obligations onto an AGPL-3.0 component elsewhere in the same product (or vice versa) — they are simply separate works under separate licenses. Llama's Community License and Gemma's Terms of Use are **not** OSI-approved open-source licenses; they are permissive-with-conditions custom agreements (commercial use is allowed, but with contractual strings: attribution/notice files, branding requirements, naming mandates for derivatives, acceptable-use-policy flow-down, and — for Llama — a MAU-based re-licensing trigger). Neither imposes copyleft/source-disclosure in the GPL/AGPL sense, so there is no direct textual conflict with AGPL-3.0, but whether AGPL's "modified source must be provided to network users" obligation could ever be read to extend to model weights trained/fine-tuned using AGPL-licensed training/inference code is a genuinely unsettled legal question in the broader industry, not specific to any one model family.

### Cited Findings
- Qwen3-4B's Hugging Face model card lists only `apache-2.0` as its license tag, with no additional terms shown on the page — [Qwen/Qwen3-4B on Hugging Face](https://huggingface.co/Qwen/Qwen3-4B).
- Phi-4-mini-instruct's model card states "The model is licensed under the MIT license" — [microsoft/Phi-4-mini-instruct on Hugging Face](https://huggingface.co/microsoft/Phi-4-mini-instruct).
- SmolLM3 base and instruct models are both Apache 2.0 per the European Open Source AI Index, which links directly to each model card's license section — [European Open Source AI Index: SmolLM](https://osai-index.eu/model/smollm).
- Mistral Small 3 and Mistral Nemo are both Apache 2.0, with Mistral's January 2025 Small 3 release marking an explicit policy shift away from the earlier Mistral Research License (which barred commercial deployment without a negotiated commercial license) — [Simon Willison on Mistral Small 3](https://simonwillison.net/2025/jan/30/mistral-small-3/), [OpenRouter Mistral Nemo listing](https://openrouter.ai/mistralai/mistral-nemo:free).
- IBM Granite 4.0 Nano family (350M-1.5B) is released under Apache 2.0 — [Pulse.bot coverage](https://www.pulse.bot/ai/news/ibms-open-source-granite-40-nano-ai-models-are-small-enough-to-run-locally-directly-in-your-browser-da21fc62-e5d0-4beb-bfdb-d5186a61c0c2/).
- Llama 3.2's Community License (mirrored on Hugging Face) grants commercial use but requires: (1) inclusion of the license agreement on redistribution, (2) a "Built with Llama" notice prominently displayed on any related website/UI/documentation, (3) retaining Meta's attribution notice in a "Notice" text file, (4) including "Llama" in the name of any distributed fine-tuned/derivative model, (5) adherence to Meta's incorporated-by-reference Acceptable Use Policy, and (6) for entities above an unspecified-in-excerpt monthly-active-user threshold as of the release date, a mandatory separate license request to Meta, grantable at Meta's sole discretion — [Llama 3.2 Community License mirror on Hugging Face](https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct/blob/main/LICENSE.txt).
- The Llama 3.2 license states derivative-work ownership vests in the user/licensee for what they create, while Meta retains ownership of the underlying Llama Materials themselves, and disputes are subject to California court jurisdiction — [Llama 3.2 Community License mirror](https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct/blob/main/LICENSE.txt).
- Gemma's Terms of Use (official ai.google.dev page, last modified per the fetched copy on April 1, 2026) requires that anyone redistributing Gemma or "Model Derivatives" must: attach the use restrictions, provide recipients a copy of the agreement, mark modified files, and ship a "Notice" file containing Google's required attribution text; use is further bounded by an incorporated-by-reference Gemma Prohibited Use Policy; the agreement grants no trademark rights to Google's names/logos; and on termination, the licensee must delete and cease use/distribution of all copies of Gemma and derivatives — [Gemma Terms of Use](https://ai.google.dev/gemma/terms?authuser=0), secondary summary — [canirun.ai Gemma license summary](https://canirun.ai/license/gemma/) (explicitly non-legal-advice).
- On the AGPL-weights question specifically: Ultralytics (maker of YOLO models) has publicly taken the position that trained model weights are a "transformation" of the training software and therefore inherit AGPL obligations from an AGPL-licensed training codebase — including the view that combining AGPL-trained weights with a non-AGPL inference script "technically does result in a combined work that is subject to the AGPL." This is the vendor's own interpretation, not a court ruling, and is contested — a parallel GitHub discussion/Hugging Face thread notes others treat weights as data rather than as a derivative work of the code — [Ultralytics GitHub issue #2129](https://github.com/ultralytics/ultralytics/issues/2129), [Roboflow: Why AGPL-3.0 Is a Risk for Computer Vision Teams](https://blog.roboflow.com/why-agpl-3-0-is-a-risk-for-computer-vision-teams/).
- The same discussion notes AGPLv3 is "an extension of GPLv3 [and] inherits its compatibility with Apache 2.0... in a one-way direction" — i.e., Apache-2.0-licensed code can generally be incorporated into an AGPL-licensed work, but not vice versa — relevant because it means combining Apache-2.0-licensed model weights/inference code (Qwen3, SmolLM3, Mistral, Granite) into a larger system that includes an AGPL-3.0 component is the compatible direction; no source found suggesting Apache 2.0 weights would need to "become" AGPL or vice versa — [dev.to: GPL AI models navigating license propagation](https://dev.to/greygoose/gpl-ai-models-navigating-license-propagation-161c).

### Inferences
- The relevant distinction for this project's AGPL-3.0-component question is: **does the LLM's own weight-license impose copyleft/source-disclosure obligations on the rest of the stack?** For Qwen3/SmolLM3/Mistral/Granite (Apache 2.0) and Phi-4-mini (MIT), the answer is clearly no — these are not copyleft licenses and have no network-use or source-disclosure clause, so they sit comfortably alongside an AGPL-3.0 component without any license-text conflict; the AGPL-3.0 component's own obligations (make corresponding source available to network users) are unaffected by, and do not affect, the permissively-licensed model weights, which are a legally separate artifact.
- For Llama and Gemma, the "conflict" risk is not a copyleft/AGPL interaction in the legal sense (their licenses don't claim network-based source-disclosure rights the way AGPL does) — it is a contractual compliance burden (branding, notices, naming, acceptable-use flow-down, and for Llama a MAU-triggered re-licensing requirement) that exists independently of the AGPL question and would need to be satisfied regardless of what other licenses are in the stack.
- The one genuinely open legal question — whether training/fine-tuning weights with an AGPL-licensed toolchain or using them inside an AGPL-licensed inference server could pull the weights themselves under AGPL's reach — is unresolved industry-wide (the Ultralytics-vs-critics debate) and is not specific to Qwen/Llama/Gemma/Mistral's own license texts; it would depend on which training/serving code the project actually AGPL-licenses and how, not on the base model's license. This is worth flagging to whoever makes the final legal call, but it is a separate question from "does the model's own license conflict with AGPL," to which the answer for all Apache-2.0/MIT candidates here is no.

### Gaps
- No primary legal opinion, case law, or official FSF/OSI guidance specifically addressing whether AGPL-3.0's network-use clause extends to fine-tuned model weights was found — only one vendor's contested blog-level position (Ultralytics) and general commentary. This is a genuinely unsettled area; do not treat the Inferences above as legal advice — a qualified IP/open-source-licensing attorney should review before any product decision hinges on it.
- Meta's and Google's primary license pages (ai.meta.com/llama, ai.google.dev/gemma/terms) were only partially fetched directly (Gemma's official terms page was reached via search summary rather than a full WebFetch in this pass; Llama's was read from a Hugging Face-hosted mirror of the license text rather than meta.com directly). Exact current wording, especially the specific MAU threshold number in the Llama license, should be re-verified against Meta's own page before finalizing a decision.
- Qwen's own LICENSE file (github.com/QwenLM/Qwen3) was not directly fetched; the Apache 2.0 determination rests on the Hugging Face model card's license metadata tag plus consistent secondary-source agreement, which is reasonably strong but not a direct read of the license file text itself.

## Specialized financial/trading-domain and agentic closed-schema models

### Takeaway
There is a small but real cluster of open-weight, finance-specialized reasoning models (Fin-R1, Agentar-Fin-R1, FinGPT, Trading-R1) that are worth noting as alternatives to a general-purpose base model, though none of them specifically targets the narrow "closed-enum decision classification" task this project needs — they are mostly built for financial reasoning/analysis/report generation rather than fixed-schema decision emission, so they would likely still need to be paired with the same constrained-decoding approach as a general base model.

### Cited Findings
- **Fin-R1** is a 7B-parameter financial-reasoning model, trained via supervised fine-tuning followed by reinforcement learning on a purpose-built 60,091-sample chain-of-thought dataset; code is public on GitHub with over 700 stars at time of the cited paper — [Fin-R1 paper (arXiv 2503.16252)](https://arxiv.org/pdf/2503.16252).
- **Agentar-Fin-R1** is a newer family (8B and 32B sizes) built directly on the Qwen3 foundation model, "engineered based on the Qwen3 foundation model to enhance reasoning capabilities, reliability, and domain specialization for financial applications" — found via secondary aggregation, not an official model card in this pass — [arXiv coverage, 2507.16802](https://arxiv.org/html/2507.16802v3).
- **FinGPT** is cited in a 2026 paper as one of several open models "adapted... to these tasks through parameter-efficient post-training," i.e., a PEFT/LoRA-adapted base rather than a from-scratch financial foundation model — [arXiv 2604.16862](https://arxiv.org/html/2604.16862v1).
- **Trading-R1** (UCLA/UW) is described as "a financially-aware model that incorporates strategic thinking and planning for comprehensive thesis composition, facts-grounded analysis, and volatility-adjusted decision making" — positioned for trading-thesis generation/analysis rather than closed-schema order decisions — [EmergentMind: FinAgent](https://www.emergentmind.com/topics/finagent) (context on related trading-agent research).
- A 2026 paper (arXiv 2604.16862) specifically trains open-weight models for direct trading execution and reports its open models "outperform open-source baselines" and "approach frontier-model trading behavior" in a chronological, multiple-choice-based trading simulation; it states the authors "open source the full training and evaluation pipeline," though the linked repository in the retrieved result was an anonymized placeholder and could not be verified further — [arXiv 2604.16862](https://arxiv.org/html/2604.16862v1).
- No model was found in this research pass that is explicitly marketed or benchmarked for the specific task framing of "closed-schema/fixed-enum agentic decision classification with `deny_unknown_fields`-style strict validation" — the financial models found target reasoning, report generation, or open-ended trading-thesis tasks, not constrained classification output.
- No open-weight model specifically benchmarked for Rust-enum-shaped structured output was found; this appears to be a generic structured-output/grammar-constrained-decoding problem rather than one any specific model family claims to solve natively, reinforcing the Section 1 conclusion that grammar-constrained decoding (not model choice alone) is the primary lever for use case A.

### Inferences
- None of the finance-specialized models found (Fin-R1, Agentar-Fin-R1, FinGPT, Trading-R1) appear to replace the need for a constrained-decoding layer for use case A; they would be better suited, if at all, as a possible base for use case B's general-chat/analysis capability (financial domain knowledge) rather than as the structured-decision classifier, and even then would need independent verification of license and tool-calling support, neither of which was found in this pass.
- Agentar-Fin-R1 being built on Qwen3 is notable: it suggests Qwen3 is already being used as a base for financial-domain fine-tunes in the community/industry, which supports Qwen3 as a reasonable foundation choice for this project's own fine-tuning effort (both for its own merits and because precedent for financial-domain adaptation already exists on that base).

### Gaps
- License terms for Fin-R1, Agentar-Fin-R1, FinGPT, and Trading-R1 were not determined in this pass — none of the sources retrieved included license information, and this would need a dedicated follow-up (checking each model's GitHub repo / Hugging Face card LICENSE file directly) before any of them could be considered for adoption given the project's AGPL-3.0 licensing sensitivity.
- No tool-calling or BFCL-style benchmark data was found for any of the finance-specialized models, so their suitability for use case B (tool-calling + chat) is unknown.
- No confirmation of parameter sizes being within the strict 1-14B "consumer hardware" range was found for Agentar-Fin-R1's larger 32B variant (32B exceeds the stated 1-14B scope and likely exceeds comfortable consumer-GPU quantized inference, though it may still run quantized on 24GB cards) — only the 8B variant is squarely in scope.

## Quantized local-serving support (llama.cpp/GGUF, Ollama, vLLM) on consumer hardware

### Takeaway
Qwen3, Gemma 3, and Phi-4-mini all have confirmed, documented presence in Ollama's model library with GGUF quantization, and all are reported runnable within 8-24GB VRAM budgets at Q4_K_M-class quantization; SmolLM3 and Mistral Nemo/Small 3 are documented as vLLM-servable with Hermes-style tool-call parsing, which is the more relevant serving path for a tool-calling use case. Exact file-size figures below come from secondary/aggregator sources rather than Ollama's or Hugging Face's own pages directly, so treat specific GB figures as approximate.

### Cited Findings
- Ollama's library hosts Qwen, Gemma, and Phi model families (general confirmation, not a specific version-by-version table) — [Mintlify Ollama models reference](https://www.mintlify.com/ollama/ollama/models).
- Qwen3 on Ollama: default tags are GGUF Q4_K_M; one secondary guide lists ~8GB for the 4B model and ~16GB at 8-bit for the 8B model, with the actual 8B GGUF download closer to ~5.2GB; the 30B-A3B MoE model (~19GB) is workable on a 24GB card only with a reduced context budget — [Spheron Network: Run Qwen3 Locally, GPU Requirements 2026](https://www.spheron.network/blog/run-qwen3-locally-gpu-requirements-2026/).
- Gemma 3 on Ollama: available in 1B, 4B, 12B, and 27B sizes; Ollama's default pull is the 4B Q4_0-quantized version; one reference lists the 4B Q4_K_M file at approximately 2.49GB — [Collabnix: How to Run Gemma Models Using Ollama](https://collabnix.com/how-to-run-gemma-models-using-ollama/), secondary size figures from [localmodel-run.pages.dev](https://localmodel-run.pages.dev/llms-full.txt) (unverified against Ollama directly).
- Phi-4-mini on Ollama: tagged `phi4-mini:3.8b`; one secondary reference lists ~2.49GB at Q4_K_M with an estimated ~3.8GB runtime footprint and 128K context — [localmodel-run.pages.dev aggregator](https://localmodel-run.pages.dev/llms-full.txt) (unverified against Ollama directly; treat as approximate).
- General consumer-hardware rule of thumb from a secondary guide: roughly 8GB VRAM for 7-8B models and 16GB for ~13B models at Q4_K_M quantization; full FP16 models require roughly 4x that VRAM — [josenobile.pages.dev Ollama/LLM guide](https://josenobile.pages.dev/guides/ollama/).
- SmolLM3-3B's model card explicitly documents vLLM serving with Hermes-style tool-call parsing: `vllm serve HuggingFaceTB/SmolLM3-3B --enable-auto-tool-choice --tool-call-parser=hermes` — [SmolLM3-3B model card](https://huggingface.co/HuggingFaceTB/SmolLM3-3B).
- Qwen3 (4B tested) is documented by community users as servable via vLLM with `--enable-auto-tool-choice --tool-call-parser hermes`, which worked where Qwen3's "native" tool-call parser mode reportedly did not (see Section 2 findings) — [Reddit r/OpenWebUI via mirror](https://redlib.hbubli.cc/r/OpenWebUI/comments/1kv0oty/qwen34b_serve_with_vllm_native_tool_call_issue).

### Inferences
- For a Rust-based local-serving architecture, llama.cpp (via GGUF) is the lower-friction path for pure inference on consumer GPUs/CPU-only setups across all of Qwen3, Gemma 3, Phi-4-mini, and SmolLM3 — all four have GGUF-quantized community or official builds and Ollama library presence; llama.cpp's GBNF grammar support is also directly relevant to solving use case A's closed-schema requirement regardless of which model is chosen.
- If tool-calling reliability (use case B) is the priority and the serving stack can run vLLM instead of/alongside llama.cpp, the Hermes-style `--tool-call-parser hermes` convention is the most consistently-documented-working path across Qwen3, SmolLM3, and (per Section 2) Hermes-branded fine-tunes themselves — this argues for standardizing the Rust agent's tool-call parsing logic on the Hermes/ReAct JSON convention rather than any one model's bespoke native format.

### Gaps
- No official Ollama library page was directly fetched in this pass (searches returned only secondary aggregators); exact current model tags, default quantization levels, and file sizes on ollama.com/library should be verified directly before finalizing a deployment plan.
- No specific data was found on Mistral Nemo/Small 3 or Granite 4.0 Nano's GGUF/Ollama packaging status — Mistral models are widely known to be GGUF/Ollama-compatible in general, but this was not independently confirmed with a citation in this research pass.
- No benchmark data comparing actual tokens/second or latency on specific consumer GPU tiers (e.g., RTX 4060 8GB vs. RTX 4090 24GB) was gathered — only VRAM-fit rules of thumb.
