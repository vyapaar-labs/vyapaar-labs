# Quantization Options and Hardware Envelope for Local 3B-14B LLMs (GGUF/llama.cpp/Ollama/vLLM, late-2026)

**Source-quality caveat (applies to the whole note):** the 2026 web is heavily saturated with templated/AI-generated "GPU for LLM" SEO sites (`willitrunai.com`, `mustafa.net`, `specpicks.com`, `gpudojo.com`, `bestllmfor.com`, `markaicode.com`, `bmdpat.com`, `toolhalla.ai`, `llmhardware.io`, `awesomeagents.ai`, `gigagpu.com`) that repeat near-identical token/s figures across completely different GPUs/models — a strong sign these are generated/extrapolated, not measured. Where a number comes only from one of these sites, it is marked **[unverified/generic]** below. Numbers from official docs (llama.cpp, vLLM), Hugging Face, arXiv/NeurIPS, and sites that show a concrete measurement methodology (e.g. `hardware-corner.net`'s per-context-length tables, a named Ollama version + GPU utilization %) are treated as more reliable but still single-source.

## What the GGUF/GPTQ/AWQ schemes mean and which fits CPU vs GPU

### Takeaway
GGUF's "K-quants" (Q4_K_M, Q5_K_M, Q6_K, Q8_0) are llama.cpp/Ollama's own mixed-precision weight formats built for CPU and CPU/GPU-hybrid inference with llama.cpp's own kernels; GPTQ and AWQ are GPU-only weight-quantization algorithms designed for vLLM/transformers GPU kernels (chiefly via the Marlin kernel on Ampere+). Q4_K_M is the de facto default "best balance" pick across sources; Q6_K/Q8_0 are near-lossless but larger; AWQ and GPTQ are roughly comparable to each other on modern vLLM, with the faster one varying by vLLM version.

### Cited Findings
- Q8_0 is reported close to lossless: on Qwen2.5-Coder-7B-Instruct, Q8_0 perplexity is 9.3061 vs 9.3071 for F16 (file size ~7723 MB) — [Hugging Face perplexity table](https://huggingface.co/ThomasBaruzier/Qwen2.5-Coder-7B-Instruct-GGUF/blob/0cdc2ebad2bc95255a27b202c5c6360cbfac23c5/perplexity.md)
- On the same table, Q5_K_M (9.3152) beats Q4_K_M (9.3699) by a measurable margin, with Q6_K between Q5_K_M and Q8_0 — [Hugging Face perplexity table](https://huggingface.co/ThomasBaruzier/Qwen2.5-Coder-7B-Instruct-GGUF/blob/0cdc2ebad2bc95255a27b202c5c6360cbfac23c5/perplexity.md)
- llama.cpp community documentation mirrors describe Q4_K_M as "the best balance of size, speed, and quality for most use cases," Q6_K/Q8_0 as the quality-first picks, Q4_0 as a legacy format superseded by K-quants, and Q2_K/IQ1_S as having "noticeable quality loss" to "near-unusable for instruction-following" — [Mistral GGUF quantization cookbook](https://docs.mistral.ai/resources/cookbooks/concept-deep-dive-quantization-methods-gguf); [llama.cpp docs mirror](https://mintlify.com/ggml-org/llama.cpp/concepts/quantization)
- vLLM's official stable docs list AWQ, GPTQ, and FP8 as supported quantization methods, with hardware support varying by GPU generation: AWQ/GPTQ run on Volta through Hopper GPUs (and some AMD/Intel/x86 CPU paths), while FP8 (W8A8) is restricted to Ada, Hopper, and AMD GPUs; Marlin kernels accelerate GPTQ/AWQ/FP8 on Ampere+ — [vLLM quantization docs](https://docs.vllm.ai/en/stable/features/quantization/), [vLLM v0.16.0 docs](https://docs.vllm.ai/en/v0.16.0/features/quantization/)
- A 2026 community benchmark found AWQ and GPTQ nearly identical under vLLM's Marlin kernel path (within ~1% latency/throughput), while a separate test reported AWQ at 741 tok/s vs GPTQ at 712 tok/s on the same hardware, and yet another found GPTQ 6-19% faster than AWQ on Qwen3-14B under vLLM 0.11.0 — the ranking "flips between benchmarks" and changes across vLLM versions — [industry 2026 quantization comparison roundup](https://blog.premai.io/llm-quantization-guide-gguf-vs-awq-vs-gptq-vs-bitsandbytes-compared-2026) (secondary aggregator, numbers not independently re-verified)
- Reported HumanEval retention: AWQ ~51.8% vs GPTQ ~46.3% in one comparison, with another source's unverified claim of "~95% quality retention for AWQ vs ~90% for GPTQ" — [2026 quantization comparison roundup](https://blog.premai.io/llm-quantization-guide-gguf-vs-awq-vs-gptq-vs-bitsandbytes-compared-2026) (unverified secondary claim)
- GGUF is described as a file container, not a quantization algorithm per se, and its vLLM throughput is reported much lower than AWQ/GPTQ (~93 tok/s for Q4_K_M in one source) — GGUF's advantage is CPU/CPU+GPU hybrid support, not raw GPU throughput — [2026 quantization comparison roundup](https://blog.premai.io/llm-quantization-guide-gguf-vs-awq-vs-gptq-vs-bitsandbytes-compared-2026) (secondary, unverified)

### Inferences
- The practical split for a local/consumer setup in 2026 is: **llama.cpp/Ollama + GGUF K-quants** for CPU-only or CPU+GPU-hybrid consumer machines (laptops, mixed VRAM/RAM), and **vLLM + AWQ or GPTQ (via Marlin)** when the whole model and KV cache fit in a single modern (Ampere-or-newer) consumer GPU and maximum GPU throughput/batching matters more than CPU fallback flexibility.
- Because AWQ vs GPTQ ranking is reported to flip by vLLM version and by model, neither should be treated as a fixed "winner" — benchmark both on the target vLLM version before committing, as several sources explicitly recommend.

### Gaps
- No official llama.cpp GitHub wiki page was retrieved directly (search only surfaced third-party mirrors); exact k-quant bit-widths-per-tensor-type specification should be cross-checked against the primary repo if precision matters.
- No apples-to-apples GGUF-vs-AWQ-vs-GPTQ benchmark on identical consumer hardware was found; all comparisons mix hardware/model/version, limiting confidence in any single number above.

## Memory footprint and tokens/sec for 3B/7B/14B models at Q4_K_M across hardware tiers

### Takeaway
At Q4_K_M, weight footprints are roughly 1.8-2.5 GB (3B), 4-5 GB (7B), and 8.5-10 GB (14B) GB, which fit comfortably on every consumer GPU tier from 8GB up and well within 16-32GB system RAM; speed scales from single digits to ~10-15 tok/s on CPU-only, to 20-70+ tok/s on 8-24GB GPUs depending on model size and context length — but almost every concrete number below comes from a single source and several directly contradict each other, so treat this as a rough envelope, not a spec sheet.

### Cited Findings
- **3B (Llama 3.2 3B, Q4_K_M):** one source's per-quant table lists Q4_K_M weights at 1.8 GB, while the same site's full-system-memory estimates for actually running it range 5.2-7.9 GB across different GPU pages; reported generation speed clusters around ~42 tok/s on most cards tested, ~48 tok/s on an NVIDIA L20, and ~57 tok/s on an RTX 5050/5090 — the repeated 42 tok/s figure across very different GPUs is flagged as likely generic/estimated rather than measured — [willitrunai.com Llama 3.2 3B pages](https://willitrunai.com/can-run/llama-3.2-3b-on-rtx-5000-ada-32gb) **[unverified/generic]**
- **7B (Q4_K_M, 8GB GPU, e.g. RTX 4060):** weights ≈4.8 GB; one vendor benchmark reports Qwen2.5-7B at 21.4 tok/s and DeepSeek-7B at 22.0 tok/s (single-stream, 512-token prompt, 256-token completion) under Q4_K_M on an RTX 4060; a different page from the same vendor reports Mistral-7B at 24-28 tok/s, while yet another page from the same site reports 55 tok/s for the same model/quant — a >2x internal discrepancy that the sources themselves flag as an outlier — [GPU hosting vendor RTX 4060 benchmarks](https://docs.bswen.com/blog/2026-03-27-rtx-4060-token-speed-benchmark-coding) (vendor blog, numbers may be favorably selected)
- **7B (Q4_K_M, 8GB GPU) memory:** a 7B Q4_K_M model plus 8K context and KV cache is estimated at ~6.4 GB total, leaving ~1.6 GB headroom on an 8GB card — [community 2026 guide, uncited methodology]
- **14B (Q4_K_M, 24GB GPU, RTX 4090):** weights ≈8.4-10 GB; reported speeds cluster 50-70 tok/s: ~58.6 tok/s for DeepSeek-R1-Distill-Qwen-14B (DatabaseMart-derived), ~49 tok/s for Qwen2.5-14B (LocalScore-derived), 55-70 tok/s general estimates for Qwen3-14B — [RTX 4090 LLM guide roundup](https://llmhardware.io/guides/rtx-4090-llm-guide) (aggregates multiple secondary sources; LocalScore and DatabaseMart figures are the most concretely sourced)
- **14B (Q4_K_M, 16GB GPU, RTX 4080):** llama.cpp measured (not estimated) throughput from `hardware-corner.net`: Qwen3-14B (Q4_K) gets ~51.2 tok/s at 16K context, dropping to ~40.6 tok/s at 32K context; prompt processing ~2,295 tok/s at 16K, ~1,395.7 tok/s at 32K — this is the most methodologically concrete GPU number found in this research pass, since it specifies context length explicitly — [hardware-corner.net RTX 4080 benchmarks](https://www.hardware-corner.net/gpu-llm-benchmarks/rtx-4080/)
- Separately, an Ollama 0.15.2 test on the same 16GB tier reported 61.85 tok/s for qwen3:14b (Q4_K_M) using 12 GB VRAM at 100% GPU utilization with a short prompt — higher than the hardware-corner.net long-context figure, consistent with throughput falling as context grows — [DEV Community RTX 4080 16GB test](https://dev.to/rosgluk/best-llms-for-ollama-on-16gb-vram-gpu-393h)
- **CPU-only, laptop, 16-32GB RAM:** no direct measured number for a 7B Q4_K_M on a modern laptop CPU was found. A theoretical-bandwidth calculation (not measured): 7B Q4_K_M (~4.2-4.5 GB) over 38 GB/s typical DDR4 laptop bandwidth caps near ~8 tok/s; over 77 GB/s DDR5 desktop bandwidth caps near ~14 tok/s — these are bandwidth-ceiling estimates, not benchmark runs — [CPU-only LLM guide, 2026] **[theoretical, not measured]**
- One measured CPU-only data point (not in the 3-14B range): TinyLlama 1.1B reached ~25-28 tok/s at Q4_K_M, CPU-only, on an Intel i5-class laptop with ~12GB RAM — [itsfoss May 2026 test, via secondary write-up] (small-model data point only; does not extrapolate reliably to 7B/14B)
- Dual-channel RAM materially matters for CPU inference: "a single 16GB stick gives half the bandwidth of 2x8GB" — [CPU-only LLM guide, 2026]

### Inferences
- The clearest, most defensible numeric anchor across the whole table is the `hardware-corner.net` RTX 4080 result (14B class, Q4_K, 40-51 tok/s depending on context length) because it states its methodology (context length swept, both generation and prompt-processing reported). Treat single-vendor-blog numbers (RTX 4060 7B figures, RTX 4090 14B figures, all 3B figures) as directional only, given the internal 2x discrepancies vendors' own pages show.
- CPU-only inference for 7B-14B models on consumer laptop RAM is very likely memory-bandwidth-bound to roughly single-digit-to-low-teens tok/s, based on the bandwidth-ceiling reasoning, but no actual measured benchmark for a 7B/14B model CPU-only was found in this pass — this is a meaningful gap given it's one of the four requested hardware tiers.
- All model sizes 3B-14B at Q4_K_M fit with room to spare on every consumer GPU tier at or above 8GB VRAM; the 8GB tier is comfortable up to ~7B and workable but tighter for 14B (weights alone ~8.5-10GB, which can exceed 8GB VRAM without CPU offload — none of the sources above actually ran a 14B model on an 8GB card).

### Gaps
- No credible, measured CPU-only tokens/sec figure for a 7B or 14B model at Q4_K_M on 16-32GB laptop RAM was found — only a theoretical bandwidth ceiling and one small-model (1.1B) data point. This is the weakest-covered cell in the requested hardware/model matrix.
- No 14B-on-8GB-GPU data point (with CPU offload) was found; it's unclear whether offloading degrades speed modestly or severely at this size/VRAM combination.
- No independently reproduced, single-source benchmark suite covering all three model sizes on all four hardware tiers exists among the sources found — the table above is stitched from different vendors/sites per cell, so cross-cell comparisons (e.g., "is 7B on 8GB faster than 14B on 16GB") should be treated cautiously.

## Quantization's effect on structured-output/tool-calling reliability specifically

### Takeaway
Aggregate accuracy metrics (task score, HumanEval-style pass rates) substantially understate quantization damage to tool-calling: controlled 2026 studies find 4-bit quantization leaves many headline scores flat while materially increasing specific failure modes — hallucinated/out-of-list tool calls, missed required tool calls, and changed arguments — and the damage is model-size- and checkpoint-dependent rather than a fixed "4-bit is safe" rule. Multiple sources converge on **structured output breaking before general fluency does** below roughly Q4/INT4, with Q3 and below being explicitly flagged as risky for schema-constrained tasks.

### Cited Findings
- **τ²-bench multi-turn agent study (arXiv preprint, Jul 2026):** "Flat Score, Amplified Failures: How the Error Budget Masks Damage in Quantized LLM Agents" (Jang, Yang, Lim, Park) tested two open-weight model families (dense + MoE) across telecom/retail domains, 456 episodes/cell, at 16/8/4-bit. Task score changes stayed within ±7.5 points and none survived multiple-comparison correction — i.e., quantization looked "free" on the standard metric. But per-call process analysis showed 4-bit quantization amplified existing failures (mainly tool-name hallucination in telecom) by up to 2.5x in volume (+17.6 points per task), while creating almost no genuinely new failure types (rank correlation ≥0.94, novel events 0.18%). Shrinking the benchmark's permitted "error budget" from ten errors to two revealed a 17-point accuracy gap that the standard metric had been absorbing — [arXiv:2607.27275](https://arxiv.org/abs/2607.27275)
- **BFCL single-turn study, "Right Tool, Wrong Arguments" (NeurIPS 2026):** across four model families, three lost at most ~2.17 points at INT4 and one gained >11 points on aggregate accuracy — yet up to 13.50% of individual per-call decisions changed between BF16 and INT4, even when the aggregate stayed flat or improved; argument-value changes outnumbered tool-selection changes ("permission drift") — [NeurIPS 2026 virtual listing](https://neurips.cc/virtual/2026/173065)
- **"Compression Breaks Discipline" (NeurIPS 2026 SLM-Agents workshop poster, Roshaan/Aaliyan/Zubair):** 600 greedy-decoded BFCL single-turn generations from Qwen3-1.7B and Qwen3-4B at FP16 vs NF4 (4-bit), with a 7-class error taxonomy. Qwen3-1.7B's missed-required-tool-call rate nearly tripled under NF4: 6.0% → 17.3% (Δ = -11.3pp, 95% CI [-17.3,-6.0], McNemar p=0.0001), across all task categories. Qwen3-4B showed **no** effect (7.3% at both precisions, CI [-4.7,+4.7]); the size-dependent interaction was itself significant (p=0.006). The authors' explicit conclusion: "4-bit safety should be validated per checkpoint instead of assumed from a size threshold." 13 of 26 NF4 misses on the 1.7B model were answered correctly at FP16, confirming quantization (not task difficulty) caused them — [NeurIPS 2026 poster 171153](https://neurips.cc/virtual/2026/171153)
- **BFCL v4 multi-turn (NeurIPS 2026, separate paper referenced in the same search cluster):** across six small models tested at F16/Q8_0/Q5_K_M/Q4_K_M, Q4_K_M dropped task accuracy meaningfully for two of the models: xLAM-2-3B 58.00% → 51.75%, Qwen3-1.7B 14.50% → 8.75% — [NeurIPS 2026 virtual listing, title not independently re-confirmed beyond search snippet]
- **Community benchmark (lower rigor, BFCL, 3 seeds + bootstrap CIs, 4GB laptop GPU):** found model *family* predicted tool-calling reliability degradation better than model *size*, and that serving backend (llama.cpp vs other) did not explain degradation beyond the quantization level itself — [DEV Community BFCL write-up](https://dev.to/happynood/does-quantization-break-tool-calling-i-measured-it-on-a-4gb-laptop-gpu-bfcl-3-seeds-bootstrap-185l) (single-hardware, not peer-reviewed; the author's own framing)
- **Long-context (~100k token) community test:** INT4 KV-cache quantization (separate from weight quantization) caused the sharpest tool-call failures in that test; INT8 KV cache appeared safer — [community write-up, single-hardware, unreviewed]
- **Structured/JSON output specifically, Qwen3.8-27B GGUF benchmark:** 4-bit variants "hold up well" for tool use; Q2_K works for conversational chat but fails code generation in 38% of cases; most tool-call failures at low bit-widths were malformed JSON delimiters (41% of failures were missing brackets/quotes); the same write-up separately reports 1-bit tool-call validity around 36% and explicitly recommends "avoiding anything below Q3 for structured output" — [Qwen3.8-27B quantization benchmark writeup](https://dailyaiworld.com/blogs/qwen38-27b-quantization-benchmarks-bit-holds-up-bit) (single blog source, internally somewhat inconsistent between its own sections)
- **Small-model fragility at even high bit-widths:** a DEV Community measurement found Llama-3.2-1B's JSON-schema validity "fragile at every quant level, including Q8_0," suggesting for very small models the floor problem is model capacity, not just quantization — [DEV Community measurement, cited via search aggregation, not independently re-fetched]
- **Commentary/opinion pieces** (not peer-reviewed, explicitly framed as argument rather than study) converge on calling structured output "the first practical casualty" below the 4-bit line, ahead of general fluency degradation — [1023jack.com "The Cliff Below Four Bits"](https://1023jack.com/market/the-cliff-below-four-bits-what-you-actually-lose-when-you-quantize-down/), [strongmocha.com mirror](https://strongmocha.com/ai-infrastructure/the-cliff-below-four-bits-how-much-do-you-really-lose/)

### Inferences
- The strongest, most rigorous evidence (the arXiv preprint and the two NeurIPS items) converges on a consistent mechanism: quantization at 4-bit does not reliably move aggregate/headline accuracy, but it does reliably change *which* calls succeed and *how* they fail (more hallucinated tool names, more missed required calls, more argument drift) — and this effect is both model- and checkpoint-dependent, not a universal threshold. This directly contradicts a naive "Q4 is fine because the benchmark score didn't move" read of quantization safety, which several of these papers call out explicitly as the trap ("error budget masks damage").
- Across all sources, there is rough convergence that **Q4/INT4 is the de facto usable floor** for structured output/tool-calling, and that **Q3 and below carry materially elevated risk** (malformed JSON, broken delimiters, missed/hallucinated tool calls) — but the "Q4 is safe" claim should be read as "Q4 is usually safe but must be validated per model/checkpoint," per the NeurIPS poster's explicit recommendation, not as a blanket guarantee.
- Smaller models (sub-2B) appear to have a schema-validity fragility problem that persists even at high bit-widths (Q8_0), suggesting that for the smallest end of the 3-14B range targeted by this research, model capacity may interact with quantization risk — i.e., a 3B model may be more sensitive to quantization-induced tool-calling degradation than a 7B or 14B model, consistent with the NeurIPS poster's explicit 1.7B-vs-4B size-dependent finding.

### Gaps
- No source in this pass tested the exact Q4_K_M/Q5_K_M/Q6_K/Q8_0 GGUF ladder specifically for tool-calling/JSON correctness with a rigorous, peer-reviewed methodology on models in the 3-14B range (the most rigorous studies used NF4/INT4 generically or FP16/Q8_0/Q5_K_M/Q4_K_M on sub-3B models). Extrapolating the "safe floor ≈ Q4" conclusion from NF4/INT4 studies to GGUF's specific K-quant scheme is a reasonable but unverified inference.
- The NeurIPS workshop poster(s) found via search are SLM-Agents workshop poster-tier publications, not full main-track NeurIPS papers — treat as early-stage peer review (poster-accepted), not as fully vetted literature.
- No source quantified structured-output degradation specifically for a 7B or 14B model (as opposed to 1.7B/4B/27B); the size range directly bracketing this research's 3-14B target is thinly covered for this specific question.

## Apple Silicon (unified memory) vs discrete consumer GPU for local 3B-14B inference

### Takeaway
Apple Silicon via llama.cpp's Metal backend or MLX is a credible, broadly competitive local-inference platform in 2026, with unified memory giving it a real sizing advantage over VRAM-capped discrete GPUs for larger models — but the MLX-vs-llama.cpp performance comparison itself is unsettled in the sources found, and all numbers here come from secondary/community benchmarks rather than Apple's own published figures (except Apple's own M5 claim, which is their own marketing claim, not independently verified).

### Cited Findings
- Apple claims roughly a 4x time-to-first-token (TTFT) improvement on M5's Neural Accelerators and ~20-30% steady-state throughput gains on M4-class chips versus the older llama.cpp Metal path — [per a 2026 MLX guide citing Apple's own claims](https://yage.ai/share/mlx-apple-silicon-en-20260331.html) (Apple's own marketing claim, not independently verified in this pass)
- A separate, independent-sounding M4 Max test found the opposite pattern for quantized models: "llama.cpp remains incredibly competitive with 4-bit quantized models," while MLX "consistently outperforms it by about 15-20%" specifically for FP16 weights — i.e., MLX's edge may be concentrated in higher-precision runs, not in the 4-bit quantized regime most relevant to this research — [digitalapplied.com MLX guide](https://www.digitalapplied.com/blog/apple-mlx-framework-local-ai-developers-2026-guide)
- On the same M4 Max, raw llama.cpp (Metal backend) was reported at 89.4 tok/s vs. Ollama's 43.5 tok/s for what appears to be the same model/config — a roughly 2x gap attributed to Ollama's own serving overhead rather than the underlying llama.cpp engine (referencing GitHub issue #14861) — [aiindigo.com comparison](https://aiindigo.com/blog/llama-cpp-vs-native-macos-inference-which-is-faster-for-apple-silicon)
- Ollama's current architecture routes by file format: GGUF files run through the llama.cpp Metal backend, while safetensors files run through MLX as a separate code path — meaning "using Ollama on a Mac" does not automatically mean using MLX — [community comparison source]
- Memory planning guidance: macOS itself reserves roughly 4-8 GB for system/apps, leaving e.g. ~38-42 GB usable out of 48 GB on an M4 Pro — a unified-memory-specific overhead that doesn't have a direct discrete-GPU analog (VRAM is typically fully usable for the model) — [bestllmfor.com M4 Pro guide](https://bestllmfor.com/meilleur-llm/m4-pro/) (the same source's 70B-on-Metal throughput estimate of 7-10 tok/s is explicitly flagged by the search summary as unverified, and is out of this research's 3-14B scope)
- Format/maturity consensus: llama.cpp/GGUF is described as "the most mature" and broadest-format option on Apple Silicon, with full K-quant/IQ-quant support; MLX is described as advantageous specifically for certain newer MoE architectures where it reportedly uses unified memory bandwidth more efficiently — [digitalapplied.com MLX guide](https://www.digitalapplied.com/blog/apple-mlx-framework-local-ai-developers-2026-guide)

### Inferences
- For the 3-14B range specifically (dense, non-MoE models, GGUF-distributed, Q4_K_M-class quantization), the evidence suggests llama.cpp/Metal remains a strong default on Apple Silicon — MLX's reported advantage concentrates in FP16 and certain MoE architectures, neither of which is the typical "quantized dense 3-14B" case this research targets.
- Unified memory's real advantage over discrete-GPU VRAM tiers is capacity flexibility, not necessarily raw speed: a 16GB/32GB/64GB M-series Mac can run a 14B (or larger) model with full-memory flexibility, whereas an 8GB discrete GPU hard-caps around 7B before requiring CPU offload — but Apple's own memory reservation (4-8GB for the OS) eats into that headline capacity number and should be subtracted when sizing.
- Given that direct, like-for-like Apple-Silicon-vs-discrete-GPU tokens/sec comparisons for 3-14B Q4_K_M models were not found in this pass (searches returned Mac-internal MLX-vs-llama.cpp comparisons, and separately Windows/Linux GPU-only benchmarks), no confident head-to-head conclusion ("M4 Pro beats/loses to RTX 4070 at 7B Q4_K_M") can be drawn from the sources gathered here.

### Gaps
- No direct, same-model/same-quant benchmark comparing an M-series Mac against a discrete consumer GPU (e.g., M4 Pro vs RTX 4070) at 7B or 14B Q4_K_M was found; this is the most significant gap for directly answering "is unified memory a meaningfully better story."
- The MLX-vs-llama.cpp comparisons found are internally conflicting (one source says MLX wins on M4 broadly per Apple's claim; another says llama.cpp "remains incredibly competitive" specifically at 4-bit and MLX only wins at FP16) — no tie-breaking primary benchmark (e.g., Apple's own published numbers, or a well-documented independent suite) was retrieved in this research pass.
- No concrete M-series tokens/sec figures for 3B/7B/14B Q4_K_M models (the specific sizes/quant this research targets) were found — only general/mixed-size commentary and one out-of-scope 70B estimate.

## Notable 2025-2026 developments in quantization worth flagging

### Takeaway
Two concrete, officially-documented 2026 developments stand out: Google's Gemma 4 QAT (quantization-aware training) checkpoint releases, which are a genuine shift toward official, vendor-trained low-bit checkpoints rather than purely post-hoc quantization; and Unsloth's "Dynamic" GGUF quantization lineage (2.0 → 3.0), a sophisticated post-training-quantization refinement (not QAT) that claims meaningful quality gains at equal file size and has become a de facto community default for GGUF quants of new model releases.

### Cited Findings
- Google released official QAT checkpoints for the Gemma 4 family on June 5, 2026, spanning sizes from a sub-1GB "E2B" edge model up to a 31B dense flagship, per most secondary coverage — though sources disagree on exact lineup: one says QAT checkpoints cover every size, another says only E2B/E4B/12B/31B got compressed-tensors checkpoints and the 26B-A4B MoE variant has no W4A16 checkpoint — [winbuzzer.com coverage](https://winbuzzer.com/2026/06/06/google-releases-smaller-gemma-4-models-for-local-ai-xcxwbn/), [rits.shanghai.nyu.edu coverage](https://rits.shanghai.nyu.edu/ai/google-ships-gemma-4-qat-models-72-less-vram-same-quality/) (sources conflict on exact size lineup — flagged explicitly)
- Memory figures for Gemma 4 QAT also conflict between secondary sources: one puts the 31B 4-bit QAT checkpoint at 17-19 GB, another says the E2B QAT checkpoint is ~1GB on disk and runs in ~3GB — [secondary coverage, exact source attribution unclear per result]; one headline claims "72% less VRAM, same quality" for the QAT release generally — [rits.shanghai.nyu.edu](https://rits.shanghai.nyu.edu/ai/google-ships-gemma-4-qat-models-72-less-vram-same-quality/) (headline claim, underlying methodology not independently verified in this pass)
- Unsloth's "Dynamic" quantization is explicitly **post-training quantization, not QAT** — it did not retrain the target model (e.g. Qwen3.8-27B) on calibration data, and did not use quantization-aware training or distillation, per one report — [secondary report on Unsloth Dynamic 3.0]
- Unsloth's own claim: Dynamic 3.0 (reported ~August 2026) achieves ">10% better top-1 accuracy at the same disk size" versus standard/rival GGUF quants for Qwen3.8-27B — this is Unsloth's own benchmark, not independently reproduced per the sources found — [Unsloth Dynamic 3.0 coverage](https://zeli.app/en/story/49365443) (vendor's own claim, unverified by a third party in this pass)
- Unsloth's own documentation states that, as of its April 20, 2026 benchmark update, it compares Dynamic 2.0 against both official QAT releases and standard imatrix quants for Qwen3.6 and Gemma 4, and states all future Unsloth GGUF uploads will use Dynamic 2.0 (superseded in messaging by Dynamic 3.0 later in 2026 per the above) — [Unsloth docs, French localization retrieved](https://unsloth.ai/docs/fr/bases/dynamic-3.0-ggufs)
- No independent head-to-head benchmark of Unsloth Dynamic quants against Google's own official Gemma 4 QAT checkpoints was found in this pass.

### Inferences
- The practical 2026 best-practice signal is: **prefer an official QAT release when the model family ships one** (e.g., Gemma 4's Google-trained QAT checkpoints), since QAT is trained to be robust to quantization rather than quantized after the fact; **fall back to a reputable community dynamic/imatrix quant (Unsloth Dynamic) when no official QAT exists** for the target model family, since these appear to meaningfully outperform naive uniform GGUF quantization at the same file size, per vendor-reported (not yet independently verified) figures.
- Given this research's earlier finding that tool-calling/structured-output reliability degrades in ways aggregate benchmarks can mask, and that this degradation is "per-checkpoint" dependent (per the NeurIPS poster), an official QAT checkpoint or a well-regarded dynamic-quant release is plausibly a meaningfully safer choice for an agentic/tool-calling workload than an arbitrary naive GGUF quant of the same bit-width — though this specific comparison (QAT/Dynamic vs naive quant, measured on tool-calling) was not directly tested in any source found.
