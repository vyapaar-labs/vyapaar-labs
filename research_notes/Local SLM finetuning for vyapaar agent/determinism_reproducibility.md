# Determinism / Reproducibility of Local LLM Serving Engines (llama.cpp, Ollama, vLLM) — late 2026

## Bottom line (read this first)

**"Same prompt + same seed + temperature=0 ⇒ byte-identical output" is NOT a safe assumption for any of the three engines in the general case.** It is achievable only under a narrower, explicitly-pinned set of conditions (same binary/build, same hardware, same thread/batch configuration, and for vLLM a specific opt-in mode). All three engines have documented, maintainer-acknowledged non-determinism even at temperature=0 / fixed seed. The dominant real-world cause is not "GPUs are random" — matmul/attention kernels are themselves repeatable for a fixed input — it is that **the batch/thread context a request is computed in varies run-to-run** (server load for vLLM, thread count for llama.cpp/Ollama-on-CPU), and reduction-order-dependent floating point arithmetic then produces a different (but each-individually-deterministic) result for a different context.

## When temperature=0/fixed seed is used, do the three engines reliably produce byte-identical output on the same hardware/software version? Documented exceptions?

### Takeaway
No engine guarantees this unconditionally, even pinning hardware and software version. vLLM's own docs say reproducibility "holds only on the same hardware and the same [vLLM] version" — and even then only under specific settings. llama.cpp has multiple maintainer-acknowledged GitHub issues where the **same seed on the same machine** produced different output solely because of thread-count-dependent floating-point reduction order. Ollama (built on llama.cpp's engine) is described by third-party guides as "non-deterministic by default," with seed treated as best-effort, not a guarantee.

### Cited Findings
- vLLM's official reproducibility usage docs state vLLM "does not guarantee reproducible results by default" because it prioritizes performance, and that reproducibility (when achieved via its recommended settings) "holds only on the same hardware and the same vLLM version" — i.e., not even nominally guaranteed cross-version/cross-hardware. — [vLLM Reproducibility docs](https://docs.vllm.ai/en/latest/usage/reproducibility.html)
- In vLLM's V1 engine, `seed` defaults to `0` and fixes `random`/`np.random`/`torch.manual_seed` per worker, and seed cannot be unset (needed for speculative decoding to stay consistent) — but this seed pinning alone does not eliminate the batch-size-dependent kernel non-determinism described below. — [vLLM Reproducibility docs](https://docs.vllm.ai/en/latest/usage/reproducibility.html)
- A controlled experiment (Thinking Machines Lab) ran the same prompt ("Tell me about Richard Feynman") 1000 times at temperature=0 against vLLM serving Qwen3-235B-A22B-Instruct-2507: default vLLM produced **80 unique completions** out of 1000 (one appearing 78/1000 times), diverging first at token 103; with their batch-invariant kernel patch, **all 1000 completions were identical**. — [Thinking Machines Lab, "Defeating Nondeterminism in LLM Inference"](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- llama.cpp GitHub issue #95 (closed): a user reported the same seed produced different text at `-t 14` vs `-t 15` threads. A maintainer confirmed: tensor ops split work differently depending on thread count, and floating-point accumulation then rounds differently across runs with different thread counts — described by the maintainer as believed-fixed on master at the time, but the underlying mechanism (thread-count-dependent reduction order) is structural. — [llama.cpp issue #95](https://github.com/ggml-org/llama.cpp/issues/95)
- llama.cpp GitHub issue #280: a user got correct answers at 4 threads but not at 8 or 10 threads, same prompt/seed; commenters linked this to the same floating-point rounding/thread-count issue as #95, and noted the thread sensitivity "is still a problem." — [llama.cpp issue #280](https://github.com/ggerganov/llama.cpp/issues/280)
- llama.cpp GitHub issue #8593: a user running `llama-cli` with a fixed seed, `-t $(nproc)` threads, and GPU offload got a *different* story on a rerun of the identical command — reported as unresolved in the thread. — [llama.cpp issue #8593](https://github.com/ggml-org/llama.cpp/issues/8593)
- A llama.cpp discussion (#22956) reports that even `--temp 0 --threads 1` was deterministic for text-only prompts but **not** for multimodal (`--image`) prompts; the user's workaround was forcing `OMP_NUM_THREADS=1`, implying a BLAS library's own internal threading was introducing additional non-determinism outside llama.cpp's own thread flag. — [llama.cpp discussion #22956 mirror](https://gh.r-mj.com/ggml-org/llama.cpp/issues/22956)
- llama.cpp's OpenAI-compatible server had a specific sampling bug (fixed in commit 65e5f6da / PR #4668): without an explicit seed, passing any non-zero temperature made output vary between requests even when the user expected determinism; the fix made default (temp 0, no seed) requests deterministic, and documented that supplying an explicit seed restores determinism when temperature > 0 is used. This confirms determinism bugs have existed even in the "intended default deterministic path." — [llama.cpp commit 65e5f6da (mirror)](https://cdn04132025.gitlink.org.cn/replica/llama.cpp/commit/65e5f6dadbba4b496bba27f573e473c66b446496)
- For Ollama, official docs (`docs/api.md`) only say "for reproducible outputs, set `seed` to a number" for `/api/generate` and `/api/chat` — there is **no explicit guarantee** in Ollama's own documentation that identical requests return identical output, and no caveats are given about hardware/version effects. — [Ollama api.md](https://github.com/ollama/ollama/blob/main/docs/api.md)
- Third-party practitioner guidance states Ollama is "non-deterministic by default," and that getting reproducible output requires **both** `temperature: 0` **and** a fixed `seed`; it also states that "full determinism across devices and versions isn't guaranteed" and treats Ollama's seed as best-effort rather than a hard guarantee. — [makandra: Ollama reproducible results](https://makandracards.com/makandra/626358-ollama-generate-reproducible-results); [respan.ai, LLM consistency](https://respan.ai/blog/llm_consistency)
- A commenter/blog note (Vincent Schmalbach) argues the seed has little direct effect under strict greedy decoding since the decoder always picks the highest-scoring token anyway — the open non-determinism at temp=0 comes from numerical noise in computing those scores, not from the sampler's RNG. — [vincentschmalbach.com](https://www.vincentschmalbach.com/does-setting-a-seed-make-llm-output-reproducible/)

### Inferences
- Since Ollama's serving engine is llama.cpp (ggml) under the hood, the llama.cpp thread-count/BLAS-threading non-determinism issues documented above are a plausible latent risk for Ollama too, though no Ollama-specific GitHub issue reproducing it was found in this research pass (see Gaps).
- "Same software version" pinning is necessary but not sufficient for any of the three engines; hardware, thread/GPU count, and (for vLLM) batching context must also be pinned.

### Gaps
- No Ollama-specific GitHub issue was found that directly reproduces thread-count-driven non-determinism (distinct from the general llama.cpp issues); this may exist but wasn't surfaced by search in this pass.
- The llama.cpp issue #95/#280 threads were from earlier in the project's history; it's unverified whether the "believed fixed on master" claim in #95 has fully eliminated thread-count sensitivity in the current (late-2026) codebase, versus just reducing its frequency. Treat llama.cpp CPU determinism as "thread-count sensitive unless explicitly pinned," not as "fixed."

## Known sources of non-determinism at temperature=0: FP non-associativity, continuous batching, quantization kernels, non-deterministic kernel autotuning

### Takeaway
The single largest, best-documented cause (per Thinking Machines Lab's analysis, now widely cited) is **lack of batch invariance in reduction-heavy kernels (RMSNorm, matmul, attention)** combined with **variable batch composition at request time** — not raw floating-point non-associativity by itself, and not atomic-add race conditions (the LLM forward pass has no atomic-add ops in normal inference). Continuous/dynamic batching in server engines like vLLM is exactly the mechanism that randomizes batch composition run-to-run; llama.cpp's simpler single-request execution model instead gets its non-determinism from CPU thread-count-dependent reduction splitting. Quantization-kernel and cuBLAS/cuDNN autotuning effects are real, plausible contributors, but this research found direct documentation mainly for the batch-invariance and thread-count mechanisms, not detailed first-party documentation isolating quantization-kernel rounding differences or kernel-autotuning non-determinism specifically.

### Cited Findings
- **(a) FP non-associativity, isolated:** Reordering float additions changes results — Thinking Machines Lab's post gives the canonical example `(0.1 + 1e20) - 1e20 = 0` vs. `0.1 + (1e20 - 1e20) = 0.1`, and reports that shuffling the summation order of a small array produced 102 distinct sums. However, the same post argues this fact alone does **not** explain server non-determinism: a fixed GPU matmul on fixed input data is run-to-run bitwise deterministic by itself. — [Thinking Machines Lab](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- **Atomic adds are not the culprit in normal inference**: most GPU kernels used in LLM forward passes avoid atomic adds via batch-parallel or split/tree reduction strategies; the post states the LLM forward pass "involves no operations that require atomic adds" (the one exception, FlashAttention backward, is a training-only op, not used in inference). — [Thinking Machines Lab](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- **(b) Continuous/dynamic batching → the real driver:** Each kernel's numeric output for a given request can depend on the batch size it is co-processed with, because batch size determines the reduction/parallelization strategy (e.g., data-parallel vs. split-K/split-reduction for matmul, or number of Split-KV chunks for FlashDecoding attention). Server load varies unpredictably request-to-request, so the batch a given request lands in is effectively random, which is why **nearly all production LLM endpoints are non-deterministic even at temperature=0**, per this analysis. — [Thinking Machines Lab](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- Kernel-level breakdown of where batch-invariance breaks (and the fixes applied): RMSNorm (split reductions used for small-batch performance break invariance; fix = one reduction strategy sized for small batches too, ~cost on large-batch perf); Matmul (Split-K and Stream-K break invariance; fix = single compiled kernel config for all shapes, reported ~20% slower than cuBLAS); Attention (must be invariant to both batch size and prefix-cache/chunked-prefill chunking; Split-KV/FlashDecoding with a variable number of splits breaks invariance; fix = fixed-size splits rather than a fixed number of splits). — [Thinking Machines Lab](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- vLLM's own "batch invariance" (beta) feature page confirms the premise directly: "Batch invariance makes model output deterministic and independent of batch size and request order," implying the default engine is **not** independent of batch size/order. Enabling it (`VLLM_BATCH_INVARIANT=1`) uses deterministic kernels for attention and other ops and disables optimizations that introduce non-determinism; it also forces a fixed custom all-reduce order under tensor parallelism (disabling FlashInfer/AITER/QuickReduce all-reduce), and splits LoRA shrink reductions into 8 fixed, fixed-order K-chunks. — [vLLM batch invariance docs](https://docs.vllm.ai/en/v0.32.0/features/batch_invariance/)
- vLLM batch-invariance caveat: under tensor parallelism, invariance is **not yet guaranteed** for all-reduces whose byte size isn't a multiple of 16 (e.g., certain hidden sizes in fp16/bf16), which can still switch between NCCL and custom all-reduce depending on batch size — i.e., even the opt-in deterministic mode has a known gap. — [vLLM batch invariance docs](https://docs.vllm.ai/en/v0.32.0/features/batch_invariance/)
- A secondary blog on this topic separately warns that vLLM's **async scheduling is on by default** and can still break batch invariance even with `VLLM_BATCH_INVARIANT=1` set, because batch membership depends on request arrival timing — this specific interaction is not addressed in vLLM's own batch-invariance docs page (confirmed absent during this research). — [Spheron Network blog](https://www.spheron.network/blog/vllm-batch-invariance-why-temperature-0-isnt-deterministic/); absence confirmed against [vLLM batch invariance docs](https://docs.vllm.ai/en/v0.32.0/features/batch_invariance/)
- **(c) Quantization kernels:** No first-party llama.cpp/vLLM/Ollama documentation was found in this research pass that isolates quantization-kernel rounding differences as a distinct, separately-quantified source of non-determinism. The one academic source found (arXiv 2506.09501) explicitly does **not** test quantized weights/INT8/INT4 — it compares only BF16/FP16/FP32 full-precision runs. — [arXiv:2506.09501v2](https://arxiv.org/html/2506.09501v2)
- **(d) cuBLAS/cuDNN kernel autotuning:** No documentation was found directly describing cuBLAS/cuDNN's own runtime algorithm autotuning as a distinct non-determinism source for these three engines specifically; Thinking Machines Lab's framing subsumes this under "different batch size → different kernel/reduction strategy chosen," which is closely related but attributed by them to batch-size-dependent kernel *selection* within the serving framework/kernel library, not specifically to cuBLAS's historical "non-deterministic algorithm selection" behavior.

### Inferences
- Of the four candidate causes listed in the brief, (b) batch-size/composition variance is the one with strong, quantified, primary-source evidence (80/1000 divergence rate collapsing to 0/1000 with batch-invariant kernels). (a) FP non-associativity is a necessary *enabling* condition but not sufficient by itself to explain run-to-run drift on a fixed-batch, single-request workload. (c) and (d) remain plausible but are evidenced only indirectly/by absence of counter-evidence in this pass.
- For llama.cpp specifically, since it typically serves one request at a time without continuous batching, cause (b) as described for server frameworks is largely inapplicable; its direct analog is thread-count-dependent reduction splitting (see llama.cpp issues #95, #280 above), which is mechanistically the same underlying phenomenon (reduction order changes with parallelization granularity) applied to CPU threads instead of GPU batch composition.

### Gaps
- No primary-source, quantitative data was found isolating quantization-kernel (e.g., Q4_K_M vs Q8_0, or CPU-quant-kernel vs GPU-quant-kernel) rounding differences as a determinism risk specifically — this is inferred as plausible by extension of the general FP-non-associativity mechanism but not directly documented for llama.cpp/Ollama/vLLM.
- No primary source was found directly confirming or ruling out cuBLAS/cuDNN non-deterministic algorithm auto-selection as an active concern in current (late-2025/2026) vLLM or llama.cpp CUDA backends specifically (as opposed to the batch-size-driven kernel-strategy-selection mechanism Thinking Machines Lab documents, which is a related but distinct claim).

## Is CPU-only inference more deterministic than GPU inference?

### Takeaway
There is no documented guarantee that CPU inference is more deterministic — and llama.cpp's own GitHub issue history shows CPU inference has its *own* well-documented non-determinism source (thread-count-dependent floating point reduction order), which is mechanistically analogous to the GPU batch-size problem. Thinking Machines Lab explicitly states their fix is GPU-kernel-focused and that **CPU kernels are not automatically batch-invariant or bitwise-reproducible either**, because they mix vectorized and non-vectorized code paths.

### Cited Findings
- Thinking Machines Lab's post explicitly caveats: "On CPUs, some kernels mix vectorized and non-vectorized intrinsics, which may not be bitwise identical," so pointwise operations are **not** automatically batch-invariant on CPU either, and the batch-invariant kernel implementation they built is GPU-focused (not validated for CPU). — [Thinking Machines Lab](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- Multiple llama.cpp GitHub issues (#95, #280) document CPU-only, same-seed, same-prompt output changing purely as a function of `-t` (thread count), because ggml's tensor-op work splitting changes with thread count and float accumulation then rounds differently — this is a CPU-specific non-determinism source, independent of any GPU. — [llama.cpp issue #95](https://github.com/ggml-org/llama.cpp/issues/95); [llama.cpp issue #280](https://github.com/ggerganov/llama.cpp/issues/280)
- A llama.cpp discussion (#22956) found that even pinning `--threads 1` was insufficient for multimodal prompts; the user had to additionally set `OMP_NUM_THREADS=1` to control a BLAS library's own internal threading — indicating CPU determinism requires pinning *multiple* independent thread-control knobs, not just llama.cpp's own flag. — [llama.cpp discussion #22956 mirror](https://gh.r-mj.com/ggml-org/llama.cpp/issues/22956)

### Inferences
- The premise "CPU is more reproducible than GPU because CPU FP execution is more sequential/reproducible" is not borne out by llama.cpp's own issue history: CPU inference is deterministic *only if thread count and all underlying BLAS threading are pinned and held constant*, which is the CPU analog of GPU batch-size pinning, not an inherently safer default. If anything, CPU-only single-request execution (as in typical llama.cpp usage) sidesteps the *continuous-batching* non-determinism source (b) that specifically affects multi-tenant GPU servers like vLLM — so for a single-user, single-request-at-a-time deployment, CPU inference (or GPU inference without continuous batching) removes one major non-determinism source, but does not eliminate FP-non-associativity-driven drift from thread/BLAS configuration changes.

### Gaps
- No direct primary-source benchmark was found quantifying "CPU vs GPU" determinism side-by-side under matched conditions (same pinned thread/batch config on each) for any of the three engines — the evidence found is indirect (CPU has its own documented non-determinism mechanism; it is not inherently immune).

## vLLM-specific: does continuous batching / PagedAttention introduce non-determinism risk beyond llama.cpp's simpler model, and what mitigations exist?

### Takeaway
Yes — this is the best-documented and most quantified non-determinism risk among the three engines. vLLM's continuous batching and PagedAttention/chunked-prefill/prefix-caching mechanics make a request's effective "batch context" vary run-to-run based on concurrent server load, which flows through batch-size-sensitive kernels (RMSNorm, matmul, attention) to produce different token-level outputs even at temperature=0 with a fixed seed. vLLM now ships an explicit opt-in mitigation (`VLLM_BATCH_INVARIANT=1`, beta as of the v0.32.0 docs checked) plus a separate, narrower fix for offline/single-process determinism (disabling V1 multiprocessing). llama.cpp's simpler single-request-at-a-time execution model does not have this specific continuous-batching failure mode (it has a different one: thread-count-dependent CPU reduction order, see above).

### Cited Findings
- vLLM's batch invariance docs state the feature's purpose is making output "deterministic and independent of batch size and request order," explicitly for "framework and model debugging, reinforcement learning rollouts, and large-scale systems that need reproducible results" — i.e., vLLM itself frames audit/reproducibility as a distinct use case requiring this opt-in mode, not the default. — [vLLM batch invariance docs](https://docs.vllm.ai/en/v0.32.0/features/batch_invariance/)
- Enabling it requires: `VLLM_BATCH_INVARIANT=1` (server: `VLLM_BATCH_INVARIANT=1 vllm serve <model>`; offline: set the env var before importing vLLM); hardware support is limited to NVIDIA GPUs with compute capability ≥8.0, AMD Instinct gfx90a/gfx942/gfx950, and Intel XPUs with Triton support (requiring the `TRITON_ATTN` attention backend). — [vLLM batch invariance docs](https://docs.vllm.ai/en/v0.32.0/features/batch_invariance/)
- Performance cost of batch invariance mode: Thinking Machines Lab's own (less-optimized) implementation measured, for Qwen3-8B on one GPU serving 1000 sequences (90–110 output tokens each): default vLLM 26s, unoptimized deterministic mode 55s, with an improved attention kernel 42s — i.e., roughly 1.6–2.1x slower, which the authors describe as "not disastrous." Secondary sources report overhead estimates in the ~30-60% range for various configurations, but these should be treated as approximate/implementation-specific rather than a fixed, citable vLLM performance guarantee. — [Thinking Machines Lab](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/); overhead range per secondary blog aggregation (not independently verified in this pass).
- vLLM's official reproducibility docs recommend, for **offline** use, either disabling V1 multiprocessing (`VLLM_ENABLE_V1_MULTIPROCESSING=0`) to make *scheduling* deterministic, or enabling batch invariance to make output insensitive to scheduling; for **online serving**, only the batch-invariance route is offered — disabling multiprocessing is not an online-serving option. — [vLLM Reproducibility docs](https://docs.vllm.ai/en/latest/usage/reproducibility.html)
- Caveat on the "disable multiprocessing" route: it has the side effect of altering the random state of the user's own Python process (vLLM updates it when workers run in-process), which is a correctness subtlety for any audit pipeline that also depends on Python-level RNG state elsewhere in the same process. — [vLLM Reproducibility docs](https://docs.vllm.ai/en/latest/usage/reproducibility.html)
- A secondary blog specifically warns that vLLM's **async scheduling, on by default,** can still break batch invariance even with `VLLM_BATCH_INVARIANT=1` set, because batch composition depends on request arrival timing, not just the batch-invariant kernels — this interaction is not mentioned in vLLM's own docs (confirmed by this research), so it should be treated as an unverified-by-vLLM-maintainers but plausible residual risk. — [Spheron Network blog](https://www.spheron.network/blog/vllm-batch-invariance-why-temperature-0-isnt-deterministic/)
- PagedAttention/prefix-caching/chunked-prefill specifically break attention-kernel batch invariance because they change how KV values are chunked per request; the Thinking Machines Lab fix required updating the KV cache and page table *before* the attention kernel runs, and switching decode-time Split-KV (FlashDecoding) from a fixed *number* of splits to fixed-*size* splits — confirming PagedAttention's chunking mechanics are a direct, named contributor to the non-determinism, not an incidental one. — [Thinking Machines Lab](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)

### Inferences
- For an audit/replay system, vLLM is the engine of the three with the most load-bearing, continuous-batching-specific non-determinism risk, but also the only one with a maintained, documented, purpose-built opt-in fix (`VLLM_BATCH_INVARIANT=1`). If vLLM is used for the backtest-replay system, this flag (plus pinning vLLM version and hardware, per vLLM's own caveat) is the closest available thing to a vendor-sanctioned reproducibility mode — but it is beta, has a documented tensor-parallel all-reduce gap, and (per secondary, unconfirmed-by-vLLM-docs reporting) may still be defeated by async scheduling unless that is also disabled/pinned.
- llama.cpp avoids this entire failure class by not doing continuous multi-request batching in the first place (for a single-stream, single-request-at-a-time audit workload, this is a structural advantage over vLLM) — at the cost of needing thread-count/BLAS-threading pinning instead.

### Gaps
- No independent, vLLM-maintainer-published benchmark of `VLLM_BATCH_INVARIANT=1` reproducibility rate (e.g., "N/N runs identical") was found; the only quantified number (1000/1000 identical) comes from Thinking Machines Lab's own research implementation, not vLLM's shipped beta feature as released in docs v0.32.0 — these may differ.
- Whether vLLM's async scheduling vs. `VLLM_BATCH_INVARIANT` interaction (claimed by the Spheron blog) is still an open issue, fixed, or was never actually true, could not be confirmed against a vLLM maintainer source in this research pass.

## Best practices for "hash the output for audit/replay" reproducibility

### Takeaway
No engine ships a single documented "audit mode" button. The cross-engine consensus pattern distilled from the sources above is: pin every layer of the stack (engine version/build, model file hash, quantization build, hardware, and request-level concurrency/batching behavior), use greedy decoding, and — where available — use the engine's specific opt-in deterministic-kernel mode (vLLM) or pin thread/BLAS-threading config (llama.cpp/Ollama). Several sources explicitly state that reproducibility is **not** guaranteed across different hardware or software versions even with everything else pinned, so a hash-for-audit system should treat "hardware+version" as part of the hash/provenance record, not assume replay will work after an engine upgrade or on different hardware.

### Cited Findings
- vLLM: reproducibility (via its documented settings) "holds only on the same hardware and the same vLLM version" — this is vLLM's own explicit scope limitation, stated directly, not an inference. — [vLLM Reproducibility docs](https://docs.vllm.ai/en/latest/usage/reproducibility.html)
- vLLM: for single-process/offline reproducibility, disable V1 multiprocessing (`VLLM_ENABLE_V1_MULTIPROCESSING=0`); for serving/online or multi-request contexts, use `VLLM_BATCH_INVARIANT=1` since disabling multiprocessing isn't an online option. — [vLLM Reproducibility docs](https://docs.vllm.ai/en/latest/usage/reproducibility.html)
- llama.cpp: pin the exact thread count (`-t`/`--threads`) and, for workloads touching BLAS-backed code paths (e.g., multimodal), also pin `OMP_NUM_THREADS`, since llama.cpp's own thread flag does not control all underlying threaded libraries. — [llama.cpp discussion #22956 mirror](https://gh.r-mj.com/ggml-org/llama.cpp/issues/22956); mechanism per [llama.cpp issue #95](https://github.com/ggml-org/llama.cpp/issues/95)
- llama.cpp server: for determinism under any temperature setting, explicitly pass a seed rather than relying on temperature=0 defaults alone — the project's own PR #4668 fix was specifically about making the OpenAI-compatible server deterministic by default at temp=0/no-seed, and documents that an explicit seed is needed once temperature > 0 is used anywhere in the pipeline. — [llama.cpp commit 65e5f6da (mirror)](https://cdn04132025.gitlink.org.cn/replica/llama.cpp/commit/65e5f6dadbba4b496bba27f573e473c66b446496)
- General practitioner guidance (not engine-specific, so treat as advisory rather than authoritative): set both `temperature=0` **and** a fixed `seed` together (seed alone is not described as a complete guarantee by any source reviewed); be aware that different engine versions/builds can still drift even with matching seed/temperature. — [makandra: Ollama reproducible results](https://makandracards.com/makandra/626358-ollama-generate-reproducible-results); [respan.ai, LLM consistency](https://respan.ai/blog/llm_consistency)
- Academic mitigation (not engine-specific; a research pipeline, not shipped in llama.cpp/Ollama/vLLM): "LayerCast" stores weights in BF16 for memory but upcasts to FP32 immediately before each matmul, keeping compute in FP32. On DeepSeek-R1-Distill-Qwen-7B it drove accuracy-variance (Std@Acc) to match full FP32 on AIME'24 (0 vs. 0.0544 for plain BF16) and near-FP32 on MATH500/LiveCodeBench-Medium, at a reported 34% memory reduction versus running fully in FP32. This demonstrates numerical precision (not just batching) is an independent, addressable lever for reproducibility, but it is not a feature of any of the three serving engines as shipped — it would need to be implemented/patched in. — [arXiv:2506.09501v2](https://arxiv.org/html/2506.09501v2)
- The same paper's experiments show full FP32 computation alone (regardless of batching/GPU count/GPU type) eliminated essentially all the measured variance in their greedy-decoding tests (Std@Acc 0 under FP32 vs. 9.15% under BF16 for the same model/task), and divergence rate dropped from 100% of examples (BF16) to 0% (FP32) — i.e., running in full FP32 precision is itself a strong (if performance-costly) reproducibility lever independent of any batching fix. — [arXiv:2506.09501v2](https://arxiv.org/html/2506.09501v2)
- Thinking Machines Lab's post, in its RL-training application, demonstrates that bitwise-identical sampling (via their batch-invariant kernels) is what allows "true on-policy RL" with trainer/sampler KL divergence staying flat at 0 — i.e., in a context directly comparable to a backtest-replay/audit system (needing the *exact* same completion reproduced by a second process), only the batch-invariant-kernel approach (not seed/temperature=0 alone) achieved exact reproduction in their tests. — [Thinking Machines Lab](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)

### Inferences
- For a SHA-256 hash-for-audit-replay use case specifically (as opposed to "get a good-enough answer"), the practical pinning checklist implied by the sources is: (1) pin exact engine binary/version, (2) pin exact model file (hash the GGUF/safetensors file itself, not just a model name/tag), (3) pin exact quantization build if quantized, (4) pin exact hardware (GPU model/count or CPU core count), (5) pin thread count and all BLAS/OMP threading env vars for CPU paths, (6) for vLLM, pin `VLLM_BATCH_INVARIANT=1` (or disable multiprocessing for strictly offline/single-process replay) and be aware of the async-scheduling caveat, (7) use an explicit seed in addition to temperature=0, (8) record the full pinned configuration alongside the hash itself as part of the audit record, since none of the three engines guarantee replay will match after any of these change.
- The strongest, most rigorously demonstrated mitigation is running in full FP32 (eliminates ~100% of the measured divergence in the one academic study found) or using vLLM's purpose-built batch-invariant kernels (eliminates divergence in Thinking Machines Lab's 1000-run test) — both come with substantial throughput cost, which is a real tradeoff for a production audit system to weigh explicitly (not a free mitigation).

### Gaps
- No source directly discusses pinning "exact quantization build" (e.g., exact GGUF quant-kernel version) as an audit practice; this is an inference from the general principle that different kernel implementations round differently, not a cited practitioner recommendation.
- No source was found describing a complete, engine-vendor-published "reproducibility checklist" for audit purposes specifically (as distinct from general ML-reproducibility advice); the checklist above is synthesized from scattered per-engine documentation, not a single authoritative source.

## Does model size (e.g. 3B vs 14B) or quantization level meaningfully change determinism risk?

### Takeaway
Evidence is thin and mostly negative/neutral: the one academic source with relevant data found that a larger model (32B) "exhibits the same reproducibility challenges" as smaller 7–8B models, i.e., no evidence that bigger models are more or less at-risk from the batching/precision mechanism — but the data is a single spot-check, not a scaling study. No source directly addresses quantization level (e.g., 4-bit vs 8-bit vs full precision) as a determinism-risk variable; the closest finding is that the general FP-precision-based mechanism makes full FP32 much more reproducible than BF16/FP16, which is suggestive that lower-precision quantization would plausibly carry similar or greater risk, but this was not directly tested in any source found.

### Cited Findings
- arXiv 2506.09501 tested model sizes only in the 7–8B range as its primary subjects, with a single secondary check on Qwen3-32B (BF16) on AIME'24, which showed Std@Acc of 5.02% (vs. 1.11% under FP32 for the same 32B model) — the paper's text states larger models "exhibit the same reproducibility challenges" as the 7–8B models, i.e., it reports *persistence* of the problem at larger scale, not elimination, but also not a clearly worse outcome. — [arXiv:2506.09501v2](https://arxiv.org/html/2506.09501v2)
- The same paper found reasoning models show larger output-length/accuracy variance than non-reasoning models — but this is a model-*type* distinction (chain-of-thought length amplifying early rounding divergence), not a model-*size* distinction, and is a potential confound for any size-based comparison. — [arXiv:2506.09501v2](https://arxiv.org/html/2506.09501v2)
- The paper explicitly does not test quantized weights (INT8/INT4/GGUF-style quantization); all experiments use BF16/FP16/FP32 full-precision weights, so there is no direct evidence from this source bearing on quantization level and determinism. — [arXiv:2506.09501v2](https://arxiv.org/html/2506.09501v2)

### Inferences
- Because the documented non-determinism mechanisms (batch-size-dependent kernel reduction strategy; thread-count-dependent CPU reduction splitting) operate at the level of *kernel implementation and execution context*, not at the level of parameter count, there is no clear theoretical reason a 3B vs 14B model should differ in determinism risk *for the same engine, same batching/thread configuration* — the risk is a property of the serving stack and numeric precision, not of model size per se. This is a reasoned inference, not a cited finding.
- Lower-precision quantization (lower mantissa bits) would be expected, by the same non-associativity mechanism documented for BF16 vs FP32, to exhibit equal-or-greater sensitivity to reduction-order changes than BF16 — but this is an extrapolation, not something any source in this research pass measured directly for quantized (as opposed to just lower-precision floating-point) weights.

### Gaps
- No source was found that directly compares determinism/reproducibility risk across different quantization levels (e.g., Q4_K_M vs Q8_0 vs FP16 in a GGUF context, or INT4 vs INT8 in a vLLM/AWQ context). This is a genuine gap — the brief's question about "meaningful difference... between different quantization levels" could not be answered with cited evidence.
- No source was found with a true scaling study (e.g., 1B/3B/7B/14B/30B all tested under matched conditions) isolating model-size effects on determinism; the only size-related data point (32B vs 7-8B) is a single spot-check in one paper, not a systematic comparison.
